## 2. Required product behavior

An invoked eat session must execute this bounded cycle:

**Receiving need -> search -> immutable qualification -> source/test inspection
-> novelty check -> receiving verification -> legal/adaptation assessment
-> selection -> another supported lead or an explicit stop -> authorised serve.**

The agent supplies semantic hypotheses, reads source as untrusted data, writes
original receiving probes and judges usefulness. The deterministic CLI validates
inputs, evidence, identities, transitions, resource accounting and effects.
It makes no model calls. The agent host drives the cycle within the user's
invocation; nothing enables scheduling or unattended autonomy.

A menu is an index into evidence. Empty menus, green miner jobs, a source packet,
a valid line range or a recorded PASS cannot establish semantic usefulness.

### 2.1 Evidence and state contract

Extend existing exploration state and serving rather than creating a second
ledger or acceptance database. Public schema additions are versioned/additive;
existing nutrient IDs, raw source occurrences, observations and votes survive.

| Record | Required information |
| --- | --- |
| Receiving need | Actual user flow; expected/observed limitation or proposed benefit; impact; selected target; default ref/SHA/worktree/policy; receiving source/test ranges; bounded backlog and confirmed pending-work check; runtime/dependency constraints |
| Lead | Need identity; provider/query/channel; native repository identity; prior exposure/lineage; proposed mechanism; qualification status; immutable source pin when acquired; source/path licence status |
| Inspection | Actual bounded donor and receiving source/test ranges; relationship confidence; available and missing channels; byte/token/range omissions; author/tool/attempt |
| Verification | Original probe or appropriate design/documentation acceptance artifact; receiving identity; expected/actual outcome; executed checks and controls; unrun/unavailable results explicit |
| Decision | Already-present, duplicate, disproved, source-supported proposal, behavior-verified finding, deferred, unsupported or held; receiving-specific reason; adaptation and maintenance cost; evidence links |
| Round | Owned attempt; planned and actually consumed action; charged requests/acquisitions/time/model use; remaining limits; next distinct lead or stopping reason |
| Selection/effect | Stable nutrient ID and receiving need/equivalence references; owner-selected effect; current policy; provider reconciliation and actual URL; later acceptance separate |

Do not rename established dispositions solely to fit this table. Add explicit
verification/evidence fields where a source-supported design finding would
otherwise be confused with an observed receiving defect.

Reviewing nominated questions and exhaustively reviewing structural seeds are
separate denominators. Scoped completion must not erase an unreviewed original
seed, unresolved licence question or missing channel. Earlier observations remain
append-only; corrections are later observations.

### 2.2 Adaptive execution and stopping

- Consume actual next actions, not just print suggestions. After already-present,
  duplicate, disproved or licence-held outcomes, try a distinct supported need or
  independently qualified source under the remaining budget.
- Persist resource charges before retryable provider effects; reconcile an
  interrupted request/publication before repeating it. Resuming cannot multiply
  budgets, requests or issues.
- Bound search requests, acquired donors, active hypotheses, replacement rounds,
  bytes, wall time and model use. A repeated exhausted lead is not a new attempt.
- Stop with an explicit reason: scoped goals met, supported frontier exhausted,
  budget exhausted, or a real unresolved external/policy/legal dependency.
  Retain the unfinished needs and deferred leads.
- A held donor stays held when an alternative is found. Do not silently weaken
  hunger, MIT-only restrictions, origin ceilings or receiving policy.
- Executed runtime probes use trusted receiving code in an owned checkout.
  Donor programs, tests, hooks, installers and builds never run.
- An architectural/documentation improvement may have an appropriate acceptance
  artifact instead of an artificial failing test. Keep design proposals distinct
  from behavior-verified changes and human acceptance.

### 4.1 Resolver result and policy

For each selected source path, expose the applicable expression, immutable
grant/notice evidence, material role and scope, obligations, supported reference
resolution, confidence/unknown reasons and actual maw mode. A conservative
repository overview remains available but is not silently substituted for a
supported path-specific answer.

Resolve references within the same immutable repository revision under explicit
depth/byte limits. Moving links, external resources, unavailable files,
symlinks/submodules and conflicting intervening package/header declarations
cannot supply unverified permission.

MIT-only qualification uses the established grant for the selected material.
An API label or MIT root cannot admit a copyleft component. A selected MIT branch
of a verified alternative expression must be explicit; AND terms, unrelated
component notices and their obligations cannot be flattened away. Unknown
applicability stays held.

COPY, COPY_FILE, REIMPLEMENT, IDEAS_ONLY and HUMAN remain separate modes.
Strict maw policy, source origin, exact materialization/clean-room receipts,
attribution and notice obligations remain enforced at the appropriate effect.
Registering a finding or filing a receiving-owned review issue is not approval
to transfer licence-held code/specifications/text.

The broader #361 REUSE precedence, arbitrary text matching under #358 and
general licence-policy redesign are not declared finished by this bounded
resolver. Complete each selected increment; leave unsupported broader acceptance
open with precise reasons.

### 4.2 Licence regression matrix

Required positive controls: canonical MIT; the NYU holder; notice-only COPYRIGHT;
the exact SARIF formatting shape; a project MIT grant followed by retained
third-party notices; an established same-grant nested path; and separated
implementation/data/specimen roles.

Required negative controls: commercial/field-of-use riders, changed operative
permission terms, additional conflicting grants, incomplete/truncated text,
ambiguous grant boundaries, unsupported metadata, restrictive suffixes,
unmapped components, unknown scopes, real restricted subtrees, missing required
notices, unsafe paths and moving/unreadable references.

Replay all seven historical held findings with actual path/grant evidence.
Report the resulting verified mode or the remaining specific blocker; do not
force every hold green. The original measured reports remain immutable.

## 8. Deterministic and host integration acceptance

Use original fixtures and inert pinned source. Extend fixture history JSON when
fixture trees change. Exercise the actual CLI and the installed skills/host
adapter; direct worker tests alone cannot qualify public command behavior.

- On each of three owned receiving fixtures, an already-present first lead,
  duplicate lead and licence-held lead cause actual supported replacement work
  and reach a distinct seeded need within the fixed budget.
- Find all supported seeded behavior gaps and verify the expected receiving
  behavior. Already-correct controls produce no novel approved change.
- A declaration that a packet/probe was examined without matching evidence is
  rejected or remains unreviewed. Unrun probes remain unrun.
- Repeated exhausted leads, unknown channels, stale receiving identity, true
  policy/legal blockers and depleted budgets stop explicitly with unfinished
  needs and original seed denominators retained.
- Kill/restart between charge/request/record and provider effect/ledger save:
  no duplicate issue, hidden spend, lost hold or rewritten observation.
- Exercise public single/multi-meal lookup, publication identity, strict policy,
  hunger, origin, notice/clean-room/materialization checks and label-independent
  marker deduplication. No provider effects occur on a refused transaction.
- Provider auth/index/rate/truncation failures remain explicit; a GitLab search
  credential never reaches GitHub or another host. Private receiving evidence
  never becomes a public donor artifact.
- Tests/lint/format/strict types, package/install smoke, CLI/plugin manifests and
  supported Windows/Linux Python 3.11/3.14 jobs pass at the resulting exact head.
  Retain quota, CodeQL and base-versus-optional dependency checks.

Do not add mandatory parser/vector/model runtime dependencies. Standard library
plus PyYAML remains the base constraint; hosted/model reasoning is an agent-host
responsibility. Compatibility and package-install paths must remain usable.

## 9. Independent usefulness and cost qualification

The version change in this specification also changes the planned comparison:

- **Baseline:** published 0.6.8 at
  915779769747908a14b1a0f7fdecdd79d16dce43 and its matching skills.
- **Candidate:** the frozen 0.6.9 release candidate and matching skills.
- The old 0.6.9.dev0-versus-0.6.7 common audit remains regression evidence.
  Do not reinterpret it as candidate discovery or reuse its known donors as
  unseen evaluation.

Before either measured arm, seal a fresh pool of ten candidate donors for each
of three receiving projects, receiving flows/needs/default and confirmed open-work
context, model/host/tool identities, policy, prior exposure and acquired facts.
Use two fresh-context independent repeats per maw/arm in balanced order:
**12 trials total**. Shared acquisition facts are allowed; shared investigation
judgments, findings and reviews between arms are not.

Preregister equal per-trial caps: **30,000 model tokens, 45 minutes, 16 provider
search requests, six donor acquisitions, 12 active hypotheses and two replacement
rounds per need**. These are proposed qualification caps, not production defaults
or authorisation to spend/run now. Any amendment is recorded and sealed before
either measured arm. Actual usage must be capturable for budget enforcement;
missing token/currency data stays unknown and cannot support an efficiency claim.

Separate review verifies novelty against receiving/default/pending work,
duplication, source/probe validity, impact, adaptation cost and legal status.
Distinguish design proposals, behavior-verified changes, and authorised human
acceptance. A runtime fix cannot count as verified from a source range alone.

Report two separate yields:

1. Independently confirmed unique actionable receiving changes, with comparable
   usefulness criteria independent of whether the producing arm resolved transfer.
2. Changes with a supported transferable mode and all required obligations.
   Removing a false licence hold improves this legal-adoption measure; it does
   not by itself establish a new discovery.

Release gates:

- At least **80%** of proposed novel actionable findings survive separate review.
  Already-present/duplicate findings do not count as novel.
- Candidate produces **more confirmed unique actionable changes overall and in
  at least two of the three maws** at equal caps, without lower confirmed precision
  or a safety/policy regression. Report actual time/tokens, legal yield and review
  variance; two repeats are an acceptance gate, not a statistical generalisation.
- All controlled supported gaps/negative cases in section 8 pass.
- Issues/PRs, CI, maintainer acceptance and default-branch retention remain
  separate actual outcomes; no adoption is inferred from publication.
- If qualification fails, 0.6.9's complete-discovery readiness remains open.
  Menu size, source-row count, green core jobs or a retrospective common audit
  cannot replace this gate. There is no minimum PR quota for an individual donor.
